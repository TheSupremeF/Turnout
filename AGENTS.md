# Product Architecture Decisions

- **Target:** one codebase, Linux/macOS/Windows, standalone for end users: no Node, Python, Rust, .NET, Docker or vendor SDK at runtime. Acceptance test: on a clean OS the app opens, builds a config plan and tests an API connection.
- **Stack:** Electron + React UI over a Rust core (`crates/*`). Electron is UI only; config editing, API calls, SSE, gateway, credentials, backup/rollback all live in Rust. The shell is `electron/main.cjs` (CommonJS on purpose: Electron's ESM loader resolves the bare `electron` specifier to npm's wrapper, so `import { app } from "electron"` fails). It serves the built GUI and the `/api/turnout/*` bridge from one ephemeral loopback port; the renderer talks HTTP only, so `src/App.jsx` has no Electron branch. Bridge code is single-sourced in `scripts/turnout-bridge.mjs`, used by both the Vite dev server and the shell. The symbol is single-sourced in `scripts/logo.mjs` (GUI, app icon, README).
- **Providers are generic (user decision, 2026-10-20):** EVREN is optional. Any service with an OpenAI-compatible or Anthropic-compatible HTTP API (OpenCode Go, OpenRouter, Ollama, custom) is added by config (`turnout providers add <id> --base-url …`). `provider-evren` is only a preset plus `/quota` and `/terms/*`.
- **Secrets (changed 2026-10-23, user decision): encrypted at rest by default.** API keys live in `vault.json` (XChaCha20-Poly1305, random 24-byte nonce), sealed under a random 256-bit data key held in the OS credential service (Keychain / Credential Manager / Secret Service). Exactly **one** OS item exists (`turnout-vault` / `vault:data-key`), so the per-item, per-build macOS prompt that made the keyring unusable does not return, and a copied data directory yields no usable secrets. No passphrase is required per command — important because the GUI Vite bridge spawns a fresh CLI process per request. `TURNOUT_CREDENTIALS` selects another backend: `file` (plain `credentials.json`, `0600` in `0700`, **not** encrypted), `keyring` (one OS item per secret, the pre-2026-10-21 design), or `vault` (Argon2id passphrase from `TURNOUT_VAULT_PASSWORD`). An upgrade from a plain-file build encrypts existing keys on first store open and renames the old file to `credentials.json.imported` (never deleted, and left in place if any key could not be copied). `turnout credentials migrate [--delete-old]` copies old Keychain items once; `turnout credentials status` lists what is stored (never secrets). Config files receive env-var *names* only; keys are injected at launch by `turnout run`. Planning refuses any plan that embeds a key-shaped token.
- **Config edits** are span patches (comments/order/unknown keys preserved), diff-first, stale-plan-checked, backed up, atomic, verified, auto-rolled-back on failure.
- **CLI and VS Code** share each harness's config file; no VS Code `settings.json` is touched (the prototype's file list showed it; the code intentionally differs).
- **Gateway** port is stable (default 47821) because harness configs embed its URL; the per-run token is injected via env.
- **Model pickers:** show the complete provider catalog returned by live discovery. EVREN model ids must match `/v1/models` exactly; the current visual prototype mirrors the last live discovery until the Rust desktop bridge replaces the snapshot. For Codex the picker ignores discovery, so Turnout writes the routed models to `model_catalog_json` (see "Facts learned").
- **OpenAI prototype catalog (verified 2026-10-20):** mirror the Codex picker order: `gpt-6.1-sol`, `gpt-6-astra`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`; use `gpt-6.1-sol` as the prototype default. “Default” is a UI preset, never a model id sent upstream. Runtime lists still come from provider discovery.
- **Multi-model routes:** a route stores `models[]` plus one default `model`. Single-model routes keep forced-model compatibility; multi-model gateways pass the selected id through, filter `/v1/models`, and reject ids outside the route. Claude uses `modelPicker.options`, OpenCode uses `provider.<id>.models`, and Codex reads the gateway catalog.
- **Multi-provider picker:** changing the provider in the GUI filters the catalog only; it must never discard selections from another provider. A harness selection may contain provider/model targets from EVREN, OpenAI, Anthropic, or any configured provider together, with one provider/model pair as the default.

- **Claude subscription is Claude Code only (verified 2026-10-21):** Anthropic forbids Pro/Max OAuth tokens in third-party apps. Turnout never copies or stores that token. The GUI labels Anthropic as "Yalnızca Claude Code" when only the subscription exists; Codex/OpenCode need a separate Anthropic API key.
- **Claude "keep original list" (hybrid):** `plan-targets claude-code --hybrid` (GUI checkbox, default on). `settings.json` points `ANTHROPIC_BASE_URL` at the gateway, keeps `modelPicker.replaceBuiltInOptions:false` and appends the custom models; no `apiKeyHelper`, token or model slots. The gateway forwards `claude-*` requests untouched to Anthropic with Claude's own credential and accepts that credential for custom models only after a free `count_tokens` probe (cached, never stored). Claude Code then depends on the Turnout Agent; `turnout rollback` returns to direct Anthropic.
- **Codex "keep original list" (hybrid, 2026-10-22, user: "Claude Code'daki gibi olmalı"):** `plan-targets codex --hybrid` (GUI checkbox "Codex’in kendi modellerini koru" on the VS Code Eklentileri card, default on). The adapter reads Codex's built-in catalog by running `codex debug models` with an empty temporary `CODEX_HOME` (the real home would return Turnout's own `model_catalog_json`), copies every built-in entry untouched (instructions, reasoning levels, hidden entries), and appends the custom models with a priority after the last built-in. Built-in ids stay bare (`gpt-6.1-sol`) and are routed to Turnout's `openai` (ChatGPT OAuth) connection, which is therefore required; added models are always namespaced (`evren/glm-5.3`). Unlike Claude's hybrid there is no credential passthrough: Codex sends only the Turnout gateway token, so the Anthropic passthrough stays Claude-only.
- **Fallback chain (2026-10-22, adopted from Bifrost's routing model):** a gateway model route carries `fallbacks: Vec<GatewayModelRoute>` (`relay-gateway`), filled by `gateway_config` with every *other* model of the same saved route, in route order. `handle_chat` walks the chain and only retries failures that another provider could plausibly fix — `RelayError::Http` and statuses 408/429/500/502/503/504/529 — never 400/401 (a bad request or bad key fails everywhere). Retry happens *before the first SSE frame*; once a partial stream reached the client the response is committed and the error is surfaced normally. The client always sees its own requested model id; the reroute is only visible as two `turnout-agent:` lines in the gateway log. Saved routes carry `fallback` (default true, `--no-fallback` to disable, GUI checkbox "Başka bir modele geç" on the extension cards), so older state files keep fallback on. Claude Code requests forwarded to Anthropic by `anthropic_passthrough` never fall back: they keep Claude's own credential and are verbatim. Tests: `crates/relay-gateway/tests/e2e.rs` (rate-limited route falls back for both streaming and non-streaming, bad model still 400, no retry).
- **Per-request log (2026-10-22):** every request the gateway finishes appends one JSON line to `<data dir>/requests/<harness>.jsonl` (`relay_gateway::RequestMeter`, `requests_dir`); `GatewayConfig.request_log` names the file and `gateway_config` sets it. A line is `ts, model (what the harness asked for), provider, upstream_model, stream, status, ms, first_frame_ms, input_tokens, output_tokens, fallback, error` — never prompts, replies or keys, and errors go through `redact_secrets`. `first_frame_ms` is time to the first *content* frame: our own opening SSE frame and `Ping`/`Usage` events do not count (counting them made the number meaningless). Files self-bound at 5000 lines by dropping the oldest half. Surfaced by `turnout history` (JSON `requests` array + a printed Requests block) and the GUI Logs page "İstekler" panel (totals + table). A meter is finished on every exit path, including client disconnect (`"client disconnected"`).
- **Supply-chain incident response (2026-10-22).** `litellm==1.107.0` on PyPI shipped a credential stealer (`cook.pth` + `cook.py` + `sitecustomize.py`, built from the lookalike repo `Berri-AI/litellm`); all 7 wheels affected, PyPI and the Docker tags pulled, `1.106.2` clean. Checked this machine: Turnout has no Python dependency; the only litellm on disk is `evren-proxy/venv` at **1.106.0**, with no `cook.*`/`sitecustomize.py` in site-packages and no `/tmp` markers. Lesson applied below rather than adding a scanner: Turnout's exposure is npm + crates + the child processes its own bridge spawns.
- **The dev bridge is a local-privilege surface (fixed 2026-10-22).** `vite.config.mjs` used to bind `0.0.0.0` and answer `/api/turnout/*` from any origin, so a page you visited could POST (Vite echoes `Access-Control-Allow-Headers: x-turnout-ui`, so the custom header was never CSRF protection) and any device on the wifi could reach it. Now `host: "127.0.0.1"` and `scripts/bridge-guard.mjs` refuses non-loopback `Host` (DNS rebinding included) and non-loopback `Origin`, and requires `x-turnout-ui: 1` on mutating requests. A missing `Origin` is allowed on purpose (curl/TUI/tests); browsers always send one on cross-origin writes. Tests: `tests/bridge-guard.test.mjs`.
- **Never send a live destructive request as a "verification".** While testing the guard I POSTed `/api/turnout/rollback` to the real dev server; it ran `turnout rollback` for real and dropped `evren/gemma-4-31b` from the Codex route. Recovered with `turnout apply --harness codex` from the saved plan. Verify guards with the unit tests or a 403-only probe, never an authenticated mutating call against the live data dir.
- **Path arguments are validated, not trusted.** `BackupId::is_safe()` (relay-core) and the `stored` filename check in `BackupStore::restore` stop `turnout rollback ../..` and a tampered manifest from reading outside `backups/`. `turnout providers add --base-url` now requires `http`/`https` with a host, so `file:`/`data:` URLs cannot be stored as a provider.
- **Redaction covers auth schemes.** `redact_secrets` used to mask only the word `Bearer` in `Authorization: Bearer <jwt>`, leaving the credential in the request log; it now masks the token that follows and recognises `gsk_`, `hf_` and `together_` prefixes.
- **Request bodies never choose a destination.** The LiteLLM SSRF advisories (GHSA-3cv6-jpf6-8222, GHSA-hx8v-g79f-8w5f) come from body fields overriding the upstream. Turnout's converter keeps only model/messages/tools, so `base_url`, `api_base`, `provider` and `user_config` in a request are dropped; a model id outside the route is a 400 before any upstream call. Regression tests in `crates/relay-gateway/tests/e2e.rs`.
- **Dependency hygiene (2026-10-22).** `npm audit` is clean: `vite` pinned to `6.4.5` (was `6.4.2`, seven launch-editor/`server.fs.deny`/middleware advisories) and `npm audit fix` moved `postcss` 8.5.31, `nanoid` 3.3.20, `source-map-js` 1.2.2, `browserslist` 4.29.4. `cargo-audit` is not installed; `Cargo.lock` carries a checksum for every third-party crate (local `relay-*`/`harness-*`/`provider-*` paths have none, correctly). Re-run `npm audit` after any dependency bump; do not add a package whose install script is not `esbuild`/`fsevents` without reading it.
- **Bifrost (maximhq/bifrost) evaluated 2026-10-22 — do not adopt as a dependency.** It is a Go, deployed LLM/MCP gateway; Turnout is a desktop config injector whose gateway exists to serve harnesses on loopback. Bifrost has no Anthropic↔chat↔Responses conversion and no Claude OAuth passthrough, which is Turnout's hard part; adding it would also break the "no runtime beyond the app" acceptance test. Adopted: the fallback chain and the per-request log above. Still worth taking later: a `/metrics` endpoint and provider presets for Bedrock/Vertex/Azure/Groq/Cerebras/Mistral/Ollama (as `turnout providers add` presets, not new code paths). Rejected: semantic cache (agent traffic must not replay answers), virtual keys/budgets/teams, MCP gateway, benchmark claims.
- **Launch profiles:** `plan-targets --profile <name>` / `turnout run <harness> --profile <name>` inject a route into one process (private gateway port, `base+10..`) without touching the harness config.
- **CLI and VS Code injection are separate product features (user decision, 2026-10-21):** the Routing screen saves a launch-only `gui-<harness>` CLI profile and must not mutate the shared harness config. The dedicated “VS Code Eklentileri” screen is the only GUI action that writes the shared config and installs/restarts the Turnout Agent. Never collapse these back into one CLI/VS Code toggle or one Apply action.
- **`turnout apply` restarts the Turnout Agent** for gateway routes; otherwise the old route keeps serving.
- **GUI hygiene:** no mock timestamps ("Son test" is the real last test time); model ids sent upstream are API ids (`claude-opus-5-5`), never display names.

Facts learned (do not regress):
- **Codex's model picker does not read the provider's models** (verified 2026-10-22, Codex 0.162.0-alpha.17.2): `model/list` in the app-server the VS Code extension drives returns the catalog compiled into the binary, *not* the gateway's `/v1/models`, and the provider's `model_catalog_url` is not used either (it expects the catalog file's schema and the OpenAI list shape fails to decode). The only working override is the top-level `model_catalog_json` file, which replaces the catalog wholesale. The harness adapter generates `<codex home>/codex-model-catalog.json` with exactly the routed models and points `model_catalog_json` at it; direct (non-gateway) routes remove that key. Verified: the extension's `model/list` then lists those ids with the right default, and `codex exec -m <id>` round-trips for each.
- `model_catalog_json` entries are strict: `slug`, `display_name`, `supported_reasoning_levels`, `shell_type`, `visibility`, `supported_in_api`, `priority`, `support_verbosity`, `truncation_policy`, `experimental_supported_tools` and `base_instructions` are all required (`codex debug models -c model_catalog_json=...` reports the next missing field).
- `gpt-5.5` is listed in Codex's built-in catalog but refuses to run on a ChatGPT OAuth account ("not supported when using Codex with a ChatGPT account"); the other seven `gpt-*` slugs work through the gateway.
- Codex 0.16x rejects `wire_api = "chat"`; it only speaks the Responses API. Chat-only providers MUST go through the gateway (`/v1/responses`).
- Codex and OpenCode may exist only as VS Code extensions (no binary on PATH). Codex ships its binary under `~/.vscode/extensions/openai.chatgpt-*/bin/<platform>/codex`; discovery scans VS Code/Insiders/Cursor/Windsurf extension dirs.
- `codex exec` waits on stdin when run without a TTY; pass `< /dev/null` in scripts.
- Claude Code needs the base URL without `/v1`, and its haiku/sonnet/opus slots pinned to the routed model.
- Claude Pro/Max OAuth cannot be treated as an Anthropic API key by Turnout. On Claude Code 2.1.153, keeping a custom `ANTHROPIC_BASE_URL` while using the official OAuth models can trigger the 1M-context/usage-credits path. A single picker can safely mix official Claude models with gateway models only when Turnout has an actual Anthropic API key; otherwise keep official Claude config direct and launch the custom provider under a separate profile/wrapper.
- Codex's tool names are `exec_command`, `write_stdin`, … (not `shell`); a wrong name comes back as "unsupported call".
- EVREN's OpenAI-compatible base URL is `https://evren-llmapi.ssyz.org.tr/v1` (`provider_evren::DEFAULT_BASE_URL`); `turnout providers add evren` needs no `--base-url`.
- OpenAI-compatible upstreams differ: some reject `stream_options` or `max_tokens`; the adapter retries once without/with the alternate parameter.
- Turnout must not depend on or install a global HTTP proxy. The old VS Code `http.proxy` / terminal `HTTP_PROXY` settings and the port-8888 SSH tunnel were removed on 2026-10-21. Loopback gateway traffic is direct.
- OpenCode 2.1.1 is now verified live: it loads the generated `turnout` provider, lists the five selected provider-aware models, and completes a real EVREN request through the background Turnout Agent while the GUI is closed. Its v2 client normally reuses a background server, so launch-only profiles must add `--standalone`; otherwise the server ignores per-process config.

Not started: Electron app, packaging/CI/signing, Windows/Linux runs, EVREN model catalog beyond discovery (do not hardcode model ids), harness test-after-apply, profiles.
Unverified: reasoning/thinking blocks against a live client.
